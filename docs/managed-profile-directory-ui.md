# Account Directory Failure UI

Add Account and the shared provider sign-in restart show structured start failures from
`ApiError.details.directoryDiagnostic`. The browser revalidates observations with the shared
closed normalizer before mapping components and reasons to fixed local copy. Unknown, malformed
and absent observations use the shared safe business-error allowlist or generic guidance; raw
peer paths, exceptions and extra fields are never rendered by this start-failure presentation.
Status-specific authorization, missing-resource, unavailable and timeout copy is also local.

The current producer emits only `manager_root`, `profiles_root`, `profile_home` and the five
reasons listed in [the transport contract](managed-profile-directory-diagnostic-transport.md).
Reserved vocabulary is compatibility handling, not evidence that future creation guarantees
landed. Uncertainty explicitly preserves directories and forbids automatic retry; it offers no
repair command or assurance of unchanged state.

Root observations offer a collapsed Local Linux Inspection disclosure. Commands are verified
against the landed `provider-profile-root-cli.ts` and `wollipog-cli.ts`: `wollipog profile-root
inspect --component manager_root|profiles_root`, and, only for a write-permission observation,
the corresponding `repair` command. These run in the affected Linux Machine's own terminal as
the runner's OS user. Repair has its own local interactive confirmation and revalidation; a
diagnostic supplies no authorization. Account directories and OS homes have no command offered.
For SSH Machines the affected host is the remote Machine, not the control-plane host.

There is no automatic retry, repair request, arbitrary path input, permission mutation or
provider launch in this UI slice. It preserves Add Account drafts, provider selection, modal
focus and cancellation, existing account/import availability and successful sign-in behavior.
It changes no backend, protocol, readiness or native account discovery behavior. Refs #4437
remains partial until the independent backend criteria are delivered.

Verification uses inert API/DOM/browser fixtures: the real client 409 seam, all current
component/reason combinations, compatibility uncertainty, malformed/unknown/missing observations,
exact business errors, restart/dismiss, preserved drafts, keyboard cancel/Escape, desktop/mobile
and light/dark layout. No real provider authentication, credentials or repair is exercised.
